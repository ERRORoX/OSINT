# Модульная архитектура OSINT Panel

## Цель

Каждый инструмент должен иметь одно понятное место в репозитории. Разработчик открывает папку инструмента и находит его описание, настройки, frontend, backend-адаптеры, тесты и документацию. Общие функции панели не копируются в каждый инструмент, а находятся в отдельном ядре.

## Каноническое расположение

Каталог `tools/<module-id>/` является домом конкретного инструмента. Например:

```text
tools/
  grabcam/
    manifest.json
    README.md
    frontend/
    backend/
    config/
    tests/
    demo/
    vendor/          # только если внутри есть сторонний исходный проект
  domain/
    manifest.json
    README.md
    frontend/
    backend/
    config/
    tests/
  username/
    ...
  photo/
    ...
  ip-rdap/
    ...
```

Не каждый модуль обязан содержать все каталоги. Пустые папки не создаются: если инструменту не нужны тесты или отдельный config, соответствующий каталог отсутствует.

Сторонние проекты (например, Sherlock, Maigret, Subfinder) остаются внутри своего каталога инструмента. Их исходный код не смешивается с кодом интеграции OSINT Panel: интеграция хранится в стандартных подпапках модуля либо временно указывается в manifest как legacy path.

## Общее ядро

`core/` содержит только код, который действительно общий для нескольких модулей:

- module registry и проверка manifest;
- общие контракты backend;
- общая навигация и маршрутизация;
- общие UI-компоненты и дизайн-система;
- общая работа с историей/рабочей областью;
- механизм обновления.

Общие компоненты не дублируются в папках инструментов. Модуль использует их через документированный интерфейс.

## Manifest

В корне каждого модуля находится `manifest.json`. Это декларативное описание, а не исполняемый код. В нём указываются:

- стабильный уникальный `id`;
- отображаемое имя, версия и категория;
- состояние миграции;
- точки входа frontend/backend;
- зависимости и необходимые системные программы;
- поддерживаемые функции и разрешения;
- старые пути, если модуль ещё не перенесён полностью.

Схема: `docs/module-manifest.schema.json`.

Discovery-слой читает manifest как данные и не исполняет код из JSON. Отдельный runtime-loader загружает только модули со статусом `integrated`, только из канонического пути `tools/<id>/backend/tool.py`, проверяет класс `ToolBase` и совпадение `tool_id`. Произвольные пути из manifest не исполняются. Модули со статусом `legacy` продолжают работать через совместимые импорты.

## Module Registry — первый рабочий слой

В проект добавлен read-only реестр `backend/module_registry.py`. Он сканирует только непосредственные каталоги `tools/<id>/manifest.json`, проверяет идентификатор, версию, категорию, статус и безопасные пути. Некорректный manifest отображается как диагностика, а не приводит к запуску его содержимого.

API для диагностики: `GET /api/modules`. Ответ содержит список найденных модулей, сводные счётчики, manifest-предупреждения и runtime-ошибки загрузки. Сам endpoint не запускает инструменты; runtime-модули загружаются один раз при инициализации центрального реестра.

Проверка unit-тестов из корня репозитория:

```bash
python -m unittest discover -s backend/tests -p 'test_module_registry.py'
```

Сейчас manifests заведены для всех 15 инструментов, присутствующих в текущем backend registry. Их статус `legacy` означает, что описание уже есть, но физический перенос frontend/backend-кода ещё не завершён.

## Module Manager в интерфейсе

Откройте `/p/modules/` или выберите «Модули» в навигации настроек. Страница запрашивает `GET /api/modules` и показывает:
- количество обнаруженных, корректных и проблемных manifest;
- состояние миграции каждого модуля;
- версию, категорию и пути точек входа;
- предупреждения и ошибки проверки.

На текущем этапе интерфейс диагностический и read-only. Он не редактирует файлы, не устанавливает зависимости и не включает/отключает runtime-инструменты. Эти операции будут добавляться только после подключения Registry к фактическому runtime и реализации безопасного управления зависимостями.

## Создание нового модуля

Для нового инструмента используйте генератор каркаса из корня репозитория:

```bash
python backend/module_cli.py create my-tool --name "My Tool" --category other
```

Генератор создаёт `tools/my-tool/` с папками `frontend/`, `backend/`, `config/`, `tests/`, а также README и manifest. Новый модуль создаётся выключенным со статусом `planned`: он не должен появляться как готовый инструмент до реализации и тестирования.

Команды разработчика:

```bash
python backend/module_cli.py list
python backend/module_cli.py check
python backend/module_cli.py runtime-check
```

- `list` — краткий список модулей и их статусов.
- `check` — полный JSON-отчёт по manifest, путям и ошибкам.
- `runtime-check` — проверяет фактическую загрузку интегрированных backend-модулей.
- `create` — безопасно создаёт каркас и не перезаписывает существующую папку.

## Примеры текущей миграции

- `tools/ip-rdap/` — первый полностью интегрированный модуль с собственными frontend, backend, README и тестами. Старый адрес и API сохранены через совместимость.
- `tools/domain-workspace/` — перенесённая интерфейсная рабочая область доменных инструментов. Она использует существующие backend-модули через стабильные API.
- Из 15 исходных backend-инструментов 6 уже имеют статус `integrated` (IP/RDAP, Domain Search, dnsx, Subfinder, Shodan, theHarvester), ещё 9 остаются `legacy` и переносятся отдельно. Domain Workspace — отдельный интегрированный frontend-модуль, который оркестрирует связанные backend-инструменты.

## Правила независимости

1. У модуля есть один владелец каталога: `tools/<module-id>/`.
2. Frontend и backend логика, принадлежащая только модулю, постепенно переезжает в этот каталог.
3. Модуль не должен импортировать внутренние файлы другого инструмента. Для общих задач используется `core/` и публичные контракты.
4. Модуль не меняет глобальную навигацию, общую шапку или updater напрямую.
5. Настройки и пользовательские данные отделяются от исходников и не должны перезаписываться обновлением.
6. Зависимости описываются модулем, но устанавливаются согласованно через общий dependency manager. Нельзя без проверки запускать `pip install` из каждого module requirements-файла.
7. Старые URL и API сохраняются через совместимые маршруты, пока все страницы не переведены.
8. Удаление или перенос legacy-файлов выполняется только после проверки всех импортов, ссылок, маршрутов и тестов.

## Этапы миграции

### Этап 1 — стандарт и инвентаризация
Зафиксировать структуру, схему manifest, список модулей и текущие legacy-пути. На этом этапе существующие страницы и backend не перемещаются.

### Этап 2 — Module Registry
Добавить безопасное чтение и проверку manifest, диагностический список модулей и отчёт о недостающих файлах. Сначала registry работает в режиме чтения и не меняет способ запуска инструментов.

### Этап 3 — эталонный модуль
Перенести один инструмент по полному циклу в его каталог, сохранив старые URL/API через адаптеры. После проверки использовать его как шаблон для следующих инструментов.

### Этап 4 — последовательная миграция
Переносить инструменты по одному: frontend, backend-адаптер, конфигурация, тесты и документация. После каждого переноса выполнять регрессионную проверку.

### Этап 5 — очистка legacy
Удалять старые файлы только когда на них больше нет ссылок и совместимость подтверждена.

## Текущее состояние репозитория

Сейчас проект ещё не является полностью модульным:

- backend-инструменты зарегистрированы вручную в `backend/tools/registry.py`;
- часть страниц находится в `static/p/`, а отдельные страницы — в `static/domain/`, `static/username/` и `static/photo/`;
- CSS и JavaScript отдельных инструментов частично находятся в общих каталогах `static/`;
- `tools/` содержит исходники сторонних CLI-проектов и некоторые собственные инструменты;
- корневой `modules/` — существующий Python-пакет, поэтому его нельзя переименовывать или использовать для новой структуры без отдельной миграции.

Поэтому перенос выполняется постепенно. До завершения миграции manifest может ссылаться на legacy-файлы. Это временный compatibility layer, а не конечная структура.

## Что не входит в текущий этап

Автономная упаковка инструмента, экспорт на флешку, portable ZIP и автономное окружение не реализуются сейчас. К ним можно вернуться отдельным этапом после завершения модульной организации.
